---
title: Authentication
description: Clerk user bearer authentication for the unified first-party API.
---

Private `/api/v1` requests use a **Clerk user session bearer**, obtained through the supported Clerk SDK:

```http
Authorization: Bearer <current_clerk_user_session_token>
```

The backend verifies the signature, issuer, lifetime and configured claim/authorized-party policy. A workspace path ID is not authorization; membership and scoped relationships are enforced server-side. A valid login can still fail authorization, fresh-authentication or eligibility checks.

Web, Android and separate Swift iOS share this user identity direction; native token-claim/authorized-party acceptance (BUILD-271) remains open, and native private screens remain locked pending their security gates. This is not evidence that every native token variant is enabled.

Some sensitive operations, including private exports and key rewrap, require signed recent authentication. Token refresh alone must not be treated as proof of a new first-factor authentication.

## Credential handling

Get the current token when making a request; do not persist it or private financial data in localStorage, query strings, logs or source control. Never use the Clerk application secret or publishable key as a user bearer. Production browser CORS currently grants only the exact dashboard origin.

## Future developer access

Paid developer keys are **deferred**. They must be issued by Clerk and gated using backend-verified Farz subscription state from the selected payment provider; Farz does not use Clerk Billing. The old instructions for90-day keys, settings controls, read scopes and globally immediate revocation were planned claims, not verified live behavior. OAuth delegation and MCP are also unavailable. Do not route first-party app users through developer keys.

## Provider signatures and browser methods

Clerk lifecycle and Resend receipt [webhooks](/docs/api/webhooks) authenticate
provider-signed original bytes using Svix headers. Their OpenAPI security schemes
are not user-bearer authentication and do not grant financial workspace access.

Production dashboard preflight permits GET, POST, PATCH and PUT with explicitly
allowed headers. PUT notification preferences are supported; lookalike origins
and cookie-based credentials are not granted access. This does not authorize the
docs origin or arbitrary third-party browsers to call private finance endpoints.
