All collection endpoints in the Farz Public Developer API utilize **deterministic cursor-based pagination**.

---

## Query Parameters

Every collection endpoint accepts the following pagination query parameters:

| Parameter | Type | Default | Limits | Description |
| :--- | :--- | :--- | :--- | :--- |
| `limit` | integer | `50` | Min `1`, Max `100` | The maximum number of items to return in the current page. |
| `cursor` | string | `null` | Max 2,048 chars | An opaque pagination token received from a prior page's `next_cursor`. |

---

## The `Page<T>` Response Structure

Collection responses wrap items in a standard generic `Page` container:

```json
{
  "items": [ ... ],
  "next_cursor": "eyJvZmZzZXQiOjUwLCJzbmFwc2hvdF9pZCI6IjEyMyJ9",
  "has_more": true,
  "meta": {
    "as_of": "2026-10-10",
    "timezone": "Asia/Dubai",
    "base_currency": "AED",
    "warnings": []
  }
}
```

- **`items`**: Array of typed records for the endpoint.
- **`next_cursor`**: Opaque cursor string for the next slice. When `null`, you have reached the end.
- **`has_more`**: Boolean flag indicating if additional records exist.

## Snapshot Boundary Rules

<Callout type="warn" title="Immutable Cursor Guarantees">
  Cursors represent an immutable query state tied strictly to:
  1. The authenticated user subject.
  2. The exact filter parameters applied on the first page.
  3. A consistent backend snapshot timestamp.
</Callout>

### Rules for Cursor Traversal:

1. **Do Not Modify Cursors**: Treat cursors as completely opaque binary blobs. Never parse, decode, or edit their contents.
2. **Preserve Filter Parameters**: When requesting the next page, pass identical query parameters (`start`, `end`, `type`, etc.) alongside the `cursor` argument.
3. **Cursor Mismatch & Expiry**: If you alter filter parameters mid-traversal or if a cursor expires, the API will return `409 CURSOR_MISMATCH` or `409 CURSOR_EXPIRED`. In either case, discard the cursor and restart your query from the beginning.

---

## Date Range Constraints

Wherever date range filtering is supported (such as transactions, valuation history, or reports):

- **Both Parameters Required**: You must supply both `start` and `end` in `YYYY-MM-DD` format.
- **Inclusive Range**: `start` and `end` dates are both inclusive.
- **366 Calendar Days Maximum**: The difference between `start` and `end` cannot exceed **366 days**. For queries spanning multiple years, break your requests into annual segments.
- **Future Dates Prohibited**: The `as_of` parameter cannot reference future dates.
