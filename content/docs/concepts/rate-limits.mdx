---
title: Rate limits
description: Current shared per-identity PostgreSQL token buckets.
---

The production unified API uses durable **per-identity token buckets** in PostgreSQL. They are shared across workers and user sessions; opening more tabs does not create more allowance. These are not the previous site's planned60-per-user/20-per-developer-credential sliding-window limits.

| Bucket | Burst capacity | Refill per minute |
| --- | ---: | ---: |
| Authenticated GET reads |120|120|
| Authenticated non-GET commands |20|30|
| Export execution/download |3|6|

Applicable export requests also consume their ordinary read/write allowance. Allowance is committed separately so a failed financial transaction does not restore it. Other public/provider/workflow protections can impose additional limits.

A429 response supplies `Retry-After` in whole seconds and the `RATE_LIMITED` envelope. If shared protection is unavailable, requests fail closed with503; it is not a reason to disable limits.

Queue requests, honor the delay, use bounded backoff with jitter and avoid unbounded polling/reload loops. Read endpoint-specific page limits from OpenAPI; there is no global promise of two concurrent reports or a366-day range for every route. Financial retries retain their original idempotency key.
