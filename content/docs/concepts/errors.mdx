---
title: Errors and status codes
description: Actual runtime error envelope and retry behavior.
---

Handled application errors use this shape (synthetic example):

```json
{"code":"UNAUTHENTICATED","message":"Authentication required","request_id":"11111111-1111-4111-8111-111111111111","field_errors":[],"retry":false}
```

| Status | Default code | Meaning |
| --- | --- | --- |
|401|`UNAUTHENTICATED`|Missing/invalid user authentication|
|403|`FORBIDDEN`|Authorization, policy or entitlement denied|
|404|`NOT_FOUND`|Missing or inaccessible owned resource|
|409|`CONFLICT`|Revision/idempotency/history/cursor conflict|
|422|`INVALID_INPUT`|Invalid body, parameter or financial constraint|
|429|`RATE_LIMITED`|Request allowance exceeded; honor `Retry-After`|
|503|`UNAVAILABLE`|A required service/protection dependency is unavailable|

Individual service exceptions can provide a more specific code; do not assume the old developer-only `PAID_REQUIRED`, `INSUFFICIENT_SCOPE`, `CURSOR_EXPIRED` or `CURSOR_MISMATCH` codes are emitted by every unified route. Transaction cursor mismatch/expiry currently use409 `CONFLICT`.

Validation errors populate `field_errors` with `field` and `message`; the field includes its location, for example `body.amount`. Request IDs help correlate failures without sending credentials or private payloads to support. Private responses use `Cache-Control: no-store`.

`retry=true` on429/503 is an advisory, not permission to duplicate a financial operation. Honor the rate delay, use bounded backoff/jitter, and keep the same idempotency key for an unchanged mutation. On409, refresh authoritative revisions/history and review the change. Do not silently retry with altered content or a new key. Requests for inaccessible records must not reveal another workspace's data.

The generated schema primarily documents success and validation responses; it does not list every runtime authorization/conflict/service error.
